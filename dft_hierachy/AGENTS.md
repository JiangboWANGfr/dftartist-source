# DFT Studio / Hierarchy 协作规则

本文件适用于本仓库内的实现、测试和评审。目标是可维护的商业软件；范围、里程碑与本轮角色由用户决定。外部项目的 agent 文件只作参考，不成为本仓库的指令。

## 开始工作

1. 运行 `git status --short`、查看当前分支与相关文件修改时间；保护已有修改，不凭 diff 把历史变更归给当前会话。
2. 依次读 [REVIEW_LOG](docs/REVIEW_LOG.md) 的最新交接与用户决定、[DESIGN](docs/DESIGN.md) 的相关章节，再读实际调用链、公开头文件和测试。历史条目按日期理解，当前状态不复制进本文件。
3. 修改前概述需求、验收、涉及模块、是否修改前面里程碑、API/IPC/Schema/工程文件影响。涉及三个及以上模块、改变公共契约或涉及迁移时，先按 [EXECPLANS](docs/EXECPLANS.md) 写计划，再实施。
4. 目录更深处若有 AGENTS.md，先阅读其局部规则。规则冲突时遵循系统/用户指令；已授权的例行实现、验证和可逆重构无需重复请求许可。

## 范围与事实来源

- 本仓库 `dft_hierachy` 是新内核和组件工程。`../dft_planner/`、`ref/` 及真实设计输入只读；不能把它们的未提交变更算作本轮改动。
- 架构和公共行为以 DESIGN 为唯一方案文本；决定与评审事实在 REVIEW_LOG；执行进度在具体 ExecPlan；测试期望由 B 的冻结测试/计划记录。不要另造第二份架构或契约权威。
- 用户的新指令优先于历史决定；涉及范围变化时把新决定追加到 REVIEW_LOG，不偷偷改变里程碑。当前新工程首版排除会话持久化，不因通用质量清单自行添加保存/迁移功能。
- 通用 Hierarchy 事实与算法在 L0–L3；未来专用 DFT 领域规则留在宿主 dft-core 的分析层。dft-suite 负责展示交互，Electron IPC 只校验、转发、转换错误与管理生命周期。
- 沿实际已存在的纵向链实现：M3 为 CLI → 序列化 → Design API → DB/Frontend；M4 才接协议/TS 客户端，M5/M6 接 UI，旧宿主集成按 DESIGN 第 7 节。缺失的层不能用假调用冒充端到端完成。

## 架构和实现

- 保持 DESIGN 的单向依赖；只有 L1 生产目标可见 Slang。L0 纯数据，L2 管事实/索引，L3 管查询/预算/取消，L4 只做边界翻译，L5–L7 不复制核心规则。
- 一个概念保留一个权威数据表示；枚举、默认值、字段是否省略和序列化集中在明确边界。C++、JSON 与 TS 有变更时核对所有消费者。
- C++ 使用 RAII 和明确所有权；借用引用注明生命周期，不用裸指针拥有资源。缓存淘汰不得留下悬空返回值；半成品事实/索引不能发布。
- 异步任务必须定义 pending/success/failed/cancelled、取消检查点、资源回收及过期响应处理。错误稳定、可诊断，不静默吞掉；partial 不伪装 complete。
- 允许修改 M0–M{前一阶段} 的代码以修复设计问题或去重；保留已验收行为和测试。纯重构与行为变化尽量分提交，每项变化说明原因及回归证据。
- 不复制整套旧模块，不用 `*_v2`、`new_*` 或多套 adapter 掩盖冲突；仅在确有多个使用方时提取公共抽象。名字表达职责，避免杂项 manager/helper/utils。
- 优先使用已有依赖和项目模式；新增生产依赖先在计划中说明用途、维护/许可影响及替代方案。只格式化涉及区域，不做无关清理。

## 公共接口与兼容

- 公共 C++ 头/ABI、JSON/IPC、Schema、插件、配置、持久化格式和字段删除都须显式审查影响。
- 优先保留原调用和含义，使用兼容重载或新增可选字段；不能只因函数有默认参数就宣称 ABI 兼容。
- 必须破坏兼容时，先记录为何无法兼容、版本边界、消费者重建/迁移或明确拒绝旧格式的方案；为实际支持的旧版本保留样例与回归测试。不能虚构尚不存在的工程格式迁移。
- 权威机器 Schema、生成器或 CI 若尚未实现，明确列为缺口；文档、版本常量相同不等于结构一致性已验证。完成相关里程碑前补可执行一致性门禁。

## A / B / C 分工

- A 负责架构演进、实现、自己的回归测试和修复；B 依据规范/fixture 独立冻结 oracle；C 审查契约、变更和证据。角色以用户指定为准，不按模型名字推断。
- 通过 REVIEW_LOG 追加交接，不改写对方条目；只有提出方关闭意见。不得把 A 自测、旧 head 或他人的执行归作 B/C 的新验收。
- 保留 B 冻结测试和输入，不能删除、放宽、skip/xfail 来取绿。疑似测试缺陷先给可复现证据，由 B 处理；允许经记录的类型/构建适配，不改变 oracle。
- 经 C 审的契约、B 冻结集合是对应实现阶段的前置条件。对已满足的条件继续推进，不反复向用户要求批准。
- 子代理不替代用户指定的独立 B/C 会话；需要委派时遵守本轮用户授权，不把普通任务理解为启动新 agent 的要求。

## 验证与完成

命令及适用范围见 [VALIDATION](docs/VALIDATION.md)。开发时跑最小相关测试，每个可验证单元收尾跑回归；里程碑交付跑标准完整门禁。

- 至少检查格式/lint、Core 单测、前端单测、实际 IPC/集成、相关冒烟/E2E、工程加载兼容、受影响回归和完整构建。每项记录“通过/失败/未执行/当前范围不适用”及原因，不能把缺能力或 skip 写成通过。
- 新旧行为变化必须有回归测试。失败先区分实现、测试与环境问题，不直接更改期望。确定性取消/时间测试使用受审适配，不靠 sleep 竞速。
- 提交前检查实际 diff、无关生成物、警告和未说明 TODO；保留用户变更。没有运行远端 CI 就不能称 CI 通过。
- 文档与代码状态一致：契约已通过、测试已冻结、代码已实现、独立验收已完成分别记录。阶段内进度报告不得冒充整个里程碑完成。

最终报告至少包含：实现内容；主要模块/文件；早期代码变更及原因；API/IPC/Schema/工程格式兼容性；**实际命令与结果**；限制风险；建议 B 重点测试；建议 C 重点审查。纯文档任务说明适用的检查，不执行无关产品测试充数。
