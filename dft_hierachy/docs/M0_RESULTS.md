# M0 结果

日期：2026-10-06 ｜ 机器：Apple M4 Pro，14 核，24 GB ｜ Slang v12.0（`545f88b2`）

M0 的内容是工程骨架、分层检查和 8 项技术假设的验证（`DESIGN.md` 9.1）。所有数字可用 `core/experiments/run_m0.sh` 复现；有固定预期的检查已注册为测试，随 `ctest` 运行。

## 1. 骨架

| 项 | 状态 |
|---|---|
| C++ 五层构建目标（`hier_model`、`hier_frontend`、`hier_db`、`hiercore`、`hier_protocol`）和命令行 `hier` | 可构建，`hier --version` 报告协议版本和前端版本 |
| C++ 分层检查 | 4 个测试分别从 model、db、query、protocol 层包含 Slang 头文件，要求因找不到头文件而编译失败；1 个对照测试确认同一文件在能看到 Slang 的目标里可以编译 |
| TypeScript 四个包（`protocol-types`、`client`、`viewmodel`、`views`） | 类型检查通过 |
| TypeScript 分层检查 | 5 条越层导入各植入一次，检查器必须报出对应规则 |
| 测试 | `ctest` 11 项全部通过；`npm run check` 通过 |

构建耗时：首次配置加构建约 1 分钟（主要是 Slang）。

TypeScript 的分层检查最初是无效的：检查器把跨包的导入边丢掉了，零违规是假的。这是靠"植入违规、要求必须报错"的反向测试发现的，修正后才生效。

## 2. 八项验证的结论

| 编号 | 假设 | 结论 |
|---|---|---|
| V1 | 共享判断正确 | **成立**。详见 `core/frontend/SHARING_VERIFIED.md` |
| V2 | 读写位段的提取方式 | **方案已选定，部分验证**：直接用 Slang 12 的分析结果；前端自己补的四项尚未验证，是 M2 的进入门槛，见 2.2 |
| V3 | 10 万实例的规模 | **在本机成立**，前提是按折叠方式遍历；没有资源预算作为判据，见 2.3 |
| V4 | 跨模块体的层次引用可识别 | **成立**，见 2.4 |
| V5 | 精度规则不比旧实现粗 | **成立**，其中 4 类比旧实现更细，见 2.5 |
| V6 | 统一的位空间 | **成立**，见 2.6 |
| V7 | 能拿到实际读入的全部文件 | **成立**，见 2.7 |
| V8 | 最长不可中断时间 | **本机数字不大**（最坏 1.2 秒）；"可接受"是我的判断，还没有预算值，见 2.3 |

### 2.1 V1：模块体共享

Slang 的判定条件已从源码逐条写出，三个设计上的差分测试零不一致，对抗样例证实了排除向上引用的必要性。三条实现上必须遵守的事项（共享标记只在完整展开后才有、被共享实例的内部没有标记、参数只能存值）都是实验中发现的，其中第三条是差分测试在 openc910 上报出 154 处不一致后定位到的。

### 2.2 V2：读写位段

原计划是自己遍历语法树。实验发现 Slang 12 的分析模块（`AnalysisManager`）已经对每个连续赋值和过程块给出：写了哪些信号的哪些位段、读了哪些信号的哪些位段、推断出的时钟。它处理了过程块里的控制流。

在 `tests/fixtures/bits/bits.sv` 上逐项核对了输出，位段全部正确。

**Slang 不提供、需要自己做的四件事：**

| 缺口 | 证据 |
|---|---|
| 网线声明初始值（`wire x = a & b;`）不算驱动 | 样例中 `init_net` 的驱动数为 0 |
| 写位段与读位段之间的对应关系，以及读的角色（数据还是条件） | 只有每个过程块整体的读集合和写集合 |
| 端口连接表达式的读 | 输出端口的驱动有，输入端口连接不作为过程块出现 |
| 分析只在规范模块体上做 | openc910 的 15848 个实例里有 15345 个没有自己的分析结果，必须经规范模块体查询 |

**决定**：读写集合以 Slang 的分析结果为准；位级对应和角色由自己的表达式遍历给出，并加一条不变量检查：自己逐位依赖的并集必须等于 Slang 的读集合。

**没有验证的部分**：上面四项和那条不变量都要有实现才能检验。M0 只确认了 Slang 一侧的输出正确，不能说连接事实的提取已经验证。进入 M2 的连接提取之前，要先有四组样例和作为强制断言的不变量测试（`DESIGN.md` 第 10 节）。

开销（在完整展开之外的增量）：openc910 上 0.18 秒，内存峰值从 425 MB 升到 642 MB。

### 2.3 V3、V8：规模与不可中断时间

| 设计 | 实例 | 不同模块体 | 完整展开 | 折叠遍历 | 内存峰值 |
|---|---:|---:|---:|---:|---:|
| `processor_core` | 122 | 17 | 0.002 s | <1 ms | 19 MB |
| `openc910` | 15848 | 503 | 0.16 s | 1 ms | 425 MB |
| 合成，全部共享 | 111112 | 7 | 0.001 s | <1 ms | 8 MB |
| 合成，1 万个互不相同的叶子 | 111112 | 11118 | 0.11 s | 3 ms | 174 MB |
| 合成，10 万个互不相同的叶子 | 111112 | 111112 | 1.18 s | 32 ms | 1676 MB |

- **成本取决于不同模块体的数量，不取决于实例数量。** 最后一行是刻意构造的最坏情况，真实设计不会每个实例都不同。
- **不按折叠方式遍历代价很大**：同一个全部共享的 10 万实例设计，逐实例遍历各自的模块体要 0.23 秒和 675 MB，深入访问后到 1416 MB；折叠遍历是 8 MB。
- **内存主要是 Slang 自己的语法树**，不是本工程的数据。只要还可能重新提取事实，Slang 的编译结果就得留在内存里。
- **V8**：最长的不可中断调用是完整展开，openc910 上 0.16 秒，最坏情况 1.18 秒。我据此判断不需要拆分检查点。
- **这些是单机测量，不是保证。** 目前没有峰值内存、打开时间、取消等待三项的预算值，所以"成立"和"可接受"只表示在这台机器上数字不大。预算在 M7 确定。

旧文档认为"完整展开是内核里最贵的操作，必须延迟"。在 Slang 12 上这不再成立（有实例缓存），打开时直接完整展开即可。

### 2.4 V4：跨模块体的层次引用

`tests/fixtures/bits/bits.sv` 中 `assign c1.poke = sel;`（从外部写入子实例）和 `assign peek = c0.poke;`（从外部读子实例）都能识别：被读写的信号所属的模块体与过程块所属的模块体不同。被写入的那个实例也正确地没有与兄弟实例共享。

两个真实设计中跨模块体的驱动数量都是 0。

### 2.5 V5：精度规则对旧实现

基准是旧工程的 wrapper 逐位依赖实现（`DesignDb.cpp`，SHA-256 前 16 位 `7c34244e5911466e`）。方法见 `DESIGN.md` 9.1，脚本是 `core/tests/fixtures/precision/compare.py`，样例是 `ops.sv`（规则表每行一个模块，共 19 个）。

| 结果 | 运算类别 |
|---|---|
| 规则表与旧实现一致 | 选择与拼接、按位运算、条件运算、缩减、比较、相等、加法、乘法、变量位移、动态位选、动态段选、函数调用、过程块 if、过程块 case |
| 规则表比旧实现更细 | 重复拼接、零扩展、符号扩展、常量位移 |
| 规则表比旧实现粗 | 无 |
| 规则表漏掉真实依赖 | 无 |
| 旧实现漏掉真实依赖 | 无 |

旧实现对加法、乘法也是"每一位依赖全部输入位"，与规则表相同。所以新规则对 wrapper 分析不会比现状差。

**构建旧后端时的发现**：旧工程在本机无法直接构建。它调用了 Tcl 8.6 才有的函数，而 macOS 自带的是 8.5，Homebrew 的 9.0 又不兼容。这就是本机那份可执行文件停在 7 月 22 日、没有 wrapper 功能的原因。本次用一个强制包含的头文件（`core/experiments/oracle/tcl85_shim.h`）补上缺的那一个函数，构建目录在新工程下，旧工程目录没有产生任何文件。

### 2.6 V6：位空间

Slang 对所有定长类型给出统一的一维位置编号，0 是最低位：

| 声明 | 写法 | 报告的位段 |
|---|---|---|
| `logic [15:8] up` | `up[11:8]` | `[3:0]` |
| `logic [0:7] rev` | `rev[0:3]`（高位端） | `[7:4]` |
| packed 结构，`lo` 是后一个成员 | `pk.lo` | `[3:0]` |
| unpacked 结构 `{a[3:0]; b[7:0]}` | `un.b` | `[11:4]` |
| `logic [3:0] arr [0:2]` | `arr[1]`、`arr[2][3:2]` | `[7:4]`、`[11:10]` |
| `logic [7:0] mem [4]` | `mem[idx]`（动态下标） | `[31:0]`（整体） |

要注意的一点：packed 结构的第一个成员在高位，unpacked 结构的第一个成员在低位。所以 `SignalInfo` 必须带每个成员的偏移和宽度，界面不能自己推算。

### 2.7 V7：输入文件名单

Slang 的源码管理器能列出编译实际读入的全部文件。在 `tests/fixtures/inputs` 上核对：嵌套两层的 include、经 `-y` 找到并被使用的库单元、filelist 文件自身都在名单里；`-y` 目录里没被用到的库单元不在。openc910 上名单是 486 个文件：filelist 列出的 485 个源文件，加上 filelist 自身。

所以 `inputHashComplete` 可以为 `true`，V7 的退路用不上。

## 3. 时钟路径上的选择逻辑怎么写

问题：第一版的时钟分析遇到用过程块（`always_comb`、`always @*`）写的选择逻辑推导不下去。这种写法在实际设计里有多常见？

方法：对每个不同的模块体，找出位于时钟或异步复位路径上的信号（它们是本地边沿触发块的时钟或异步控制，或者连到子实例的这类端口，并沿组合驱动源向后传递），再统计驱动这些信号的组合驱动源是怎么写的。实现是 `hier_exp clockstat`，在 `tests/fixtures/clockpath/selectors.sv` 上核对过每一类的计数。

| 驱动源的写法 | `processor_core`（17 个模块体） | `openc910`（503 个模块体） |
|---|---:|---:|
| `assign`，直接连接 | 4 | 16 |
| `assign`，反相 | 2 | 0 |
| `assign`，门（二元运算） | 0 | 5 |
| `assign`，选择器（`?:`） | 0 | 1 |
| `assign`，其他表达式 | 0 | 5 |
| **过程块里的 if/case 选择** | **0** | **0** |
| 寄存器输出用作时钟或复位 | 0 | 1 |

**两个设计里，时钟和异步复位路径上都没有用过程块写的选择逻辑。**

局限：
- 只统计了两个设计。
- 路径不穿过 blackbox。如果时钟经过一个没有源码的库单元，它上游的逻辑不在统计内。
- 时钟和异步复位合在一起统计。

## 4. 对设计的影响

以下各项已回写 `DESIGN.md`：

1. **打开时直接完整展开**，不做延迟展开。全设计索引几乎立刻就绪。
2. **读写集合用 Slang 的分析结果**，自己只做位级对应、角色、初始值和端口连接。
3. **遍历必须走规范模块体**；参数只存值。
4. **`SignalInfo` 带成员的偏移和宽度。**
5. **打开选项要支持**：全部文件作为一个编译单元（openc910 的宏定义在作为源文件列出的头文件里）；未知模块当作 blackbox 而不是错误。两项都不开时 openc910 有 2756 个错误，都开之后是 0 个。这两项旧工具都是默认行为。

## 5. 没有做或没有核实的

- 性能数字只在这一台机器上测过，没有在 Linux 上测。
- 香山等更大的真实设计按计划推到 M7。
- `processor_core` 编译时有 23 个"未定义 timescale"的错误，不影响展开和上面的结果。M1 要决定把它降为警告还是提供默认 timescale。
- V2 的位级对应和角色还没有实现，只确定了方案；"自己的并集等于 Slang 的读集合"这条检查要到 M2 才能运行。
- V5 只比较了规则表与旧实现；"新实现的输出等于规则表"要到 M2。
